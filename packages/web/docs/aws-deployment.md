# Historical single-service AWS deployment runbook

**Status: historical, retired October 10, 2026.** New AWS installations use the standalone [PostgreSQL/conversation-worker module](https://github.com/dispatchlabs-ai/terraform-aws-dispatch). This document preserves the earlier SQLite candidate procedure, not a supported alternative AWS installation path. This runbook supports [WP-041](handoff.md#workers-and-deployment), not a claim of deployability. This procedure covers the earlier single-service ECS Fargate, ALB and S3 Files candidate, not the newly accepted per-conversation workers/Postgres target. Keep its persistent-mount requirements for that SQLite candidate; they are not requirements for disposable-workspace workers. The candidate module and OCI wrapper exist; isolated amd64 startup/shutdown passed as recorded in WP-041, but ARM execution, persistent-state/network qualification, live consumer-plan review and AWS qualification remain pending. See the [module interfaces](../infra/aws/README.md) for inputs/outputs; resolve the remaining operator transport before use. The application owns this generic procedure; installation-specific plans, secret references and evidence belong in the caller's infrastructure repository.

## Before applying

1. Build `nix build .#packages.aarch64-linux.oci` for the default ECS ARM64 target, or `.#packages.x86_64-linux.oci` with explicit `cpu_architecture = "X86_64"`, on a matching Linux builder or approved emulation, inspect its actual layers, load/run it using the candidate read-only-root and mounted-state settings, and publish to the caller's registry. Apple Silicon evaluation or host-package builds are not image builds. Pin the application image by registry digest and the module by an immutable revision. Record Linux architecture, source revision, Terraform/OpenTofu and AWS provider versions. Validate the example with both engines; use one engine consistently for the installation's state. Record native versus emulated execution separately. Publish a multi-platform OCI index only after both Linux images are inspected and qualified; record its digest and both child digests.

2. Select the final HTTPS origin and certificate before enrollment. The origin hostname determines the passkey relying-party ID; changing domains requires passkey re-enrollment. Supply caller-owned network, cluster and filesystem inputs; verify outbound access for image/log delivery, storage and model/MCP providers.
3. Review the concrete plan and estimated recurring cost, including ALB, tasks, storage and logs. Choose `log_kms_key_arn` and `log_retention_days` deliberately: logs may contain conversation-derived data. Reject unexpected replacements/deletions. Review storage retention and eventual teardown separately; do not assume destroying infrastructure preserves data. Apply only after authorization for that plan.
4. Review task ingress from the ALB only, HTTPS-only port 443 (the module has no port-80 redirect), health check `/`, at most one service task and stop-before-start deployment. The module defaults `desired_count=0`, an internal ALB and private task addressing; review client CIDRs, routes and egress before choosing a public ALB. Task egress defaults to all traffic; narrow the caller's policy while preserving TCP 443 for direct S3 reads/AWS and model/MCP APIs, DNS, and TCP 2049 to the storage mount-target security group. Use a security-group reference for 2049 where supported; an S3 VPC endpoint does not replace the mount path. Verify required provider/MCP destinations rather than assuming this baseline covers every integration. Confirm SIGTERM drainage fits the task's shutdown allowance. Keep ECS Exec disabled unless an explicit operator procedure authorizes temporary enablement and its additional permissions.
5. Review execution-role permissions separately from the application task role. Coding tools can obtain task-role credentials, so installation access-point and backing-prefix scope must be enforced and qualified. S3 direct read/version-read/list grants bypass filesystem POSIX permissions; ownership modes do not narrow these AWS permissions. The entire installation prefix is secrets-bearing, including provider authorization under `/data/home/.pi/agent`. `GetObjectVersion` can expose noncurrent versions of deleted files or revoked credentials; review the caller-owned version-retention/lifecycle policy and document its recovery/privacy tradeoff before real accounts. Do not add general AWS administration or backup-read permissions for convenience.

## Persistent state and bootstrap

The candidate image/module contract is UID/GID 65532 with one access point at `/data`, `DISPATCH_DATA_DIR=/data/state`, `DISPATCH_WORKSPACE_DIR=/data/workspace`, and `HOME=/data/home`; writable ephemeral `/tmp` and a read-only image root. The OCI entrypoint creates writable home/state/workspace directories and then execs the requested command. Verify mounted-directory ownership at runtime. The access-point root is `/dispatch/NAME/data`; changing the module name/root requires deliberate migration, not an assumption that existing state will follow. Do not treat ephemeral task storage as persistence.

Start with fresh company state. Never copy a personal development state directory, provider authorization or personal MCP credentials into a shared installation. Agree which repositories, tools and external identities may be shared. Coding workspaces are not sandboxes: agents can access all service-readable files, including other users' secrets and task-role credentials.

Provision deployment-specific model credentials and operator MCP configuration through the reviewed runtime mechanism, not image layers, command arguments, source control or plaintext Terraform values. Module `secret_environment` accepts exact Secrets Manager/SSM ARN references for execution-role injection; ordinary `environment` values are non-secret and enter infrastructure state. Runtime-critical environment names are reserved. Resolved secret environment values are readable by coding-agent shells, not just the server; only inject authority approved for every conversation using coding tools. Provider credentials may live in the configured Pi agent directory (default `$HOME/.pi/agent`); environment-based provider authorization supported by Pi is a separate operator choice. Record which mechanism is actually used without recording secret values.

For enrollment, use the packaged `dispatch-auth` CLI with the same origin/company/data settings; see [account provisioning](usage-guide.md#first-account-and-sign-in). The Fargate operator invocation is pending implementation. Stop the service, scale it to zero and confirm every prior task is STOPPED before any enrollment, recovery, backup or integrity task opening its databases. `dispatch-auth` does not take the runtime lock; authentication opens and modifies state before service ownership admission, and shutdown releases that lock before all stores close. MCP database initialization occurs after admission. Never use lock release alone as evidence of complete process exit. Generated invitation links are secrets: deliver privately to their intended owners and never retain them in plan logs or deployment evidence. There is no default password.

## First-deployment gate

Use an isolated access point/prefix and disposable accounts/credentials. Follow [SQLite qualification](aws-sqlite-qualification.md); retain stop-before-start even if overlap exclusion passes. Confirm separate filesystem clients, abrupt termination, integrity and application continuity, backup/restore and task-role negative authorization checks. Do not publish credentials, invite links, account data or authenticated captures as evidence.

Record exact module/image/provider revisions, client topology, stop/exit timestamps, observations and failures in WP-041 or link sanitized evidence from the installation root. Successful builds, healthy ALB targets and prior local infrastructure experiments do not establish this application's storage safety. Failures block real-data enrollment until resolved; do not relax the lock or switch to ephemeral storage to make deployment green.

## Upgrade and rollback

1. Review the new image/module plan and migration compatibility. Record the last known-good image digest and restorable backup. Do not assume an older image can read migrated state.
2. Stop admission, scale service to zero and confirm all tasks using this store have exited. A stop request is not evidence of exit. Disable independent maintenance/qualification tasks and scheduled replacements before touching files.
3. Take a complete stopped-service backup. Apply the reviewed replacement with no overlapping writer; restore the service to one task and observe health, sign-in, MCP credentials, attachments and committed conversations.
4. If startup/recovery fails, scale to zero and confirm exit again. Preserve the newer store privately before rollback. Revert only to a digest proven compatible with that store, or restore the matching complete pre-upgrade backup to an isolated empty destination before starting its matching image. Restoring older state discards subsequent writes; obtain operator approval for that loss. Never point two running services at the restored store.

## Backup and restore

The module destroys its service, ALB, access point and roles, but not caller-owned storage or retained task-definition revisions. Preserve recovery access and pins before destroy; physical data deletion is a separate explicit action. Caller-owned filesystem/bucket policies, encryption/KMS, mount connectivity and backups must agree with the generated task-role/security-group settings. See the module README for the exact scoped S3 read/list and S3 Files permissions.


Preserve the complete `DISPATCH_DATA_DIR`: `auth.sqlite` plus `auth.key`, `connections.sqlite` plus `connections.key`, operator connection configuration, and the entire `runtime/` tree including Pi metadata and attachment blobs. Also preserve the workspace, configured Pi agent directory/provider authorization and any separately referenced operator credential files under their own restricted backup policy. Capture installation configuration and image/module pins without secret values. SQLite keys, databases and blobs form one restore set; rebuilding the image cannot recover missing keys or attachments.

An installation backup supports restart/recovery, not live-machine migration: stored conversations and task state can travel, but running shell processes, network connections and external-service state do not. Stop the source before starting a migrated destination. Use disposable state and credentials for rehearsals; separate copies of a store can otherwise resume the same pending external actions. Qualify unfinished-work recovery separately from file restoration.

Existing conversations persist absolute coding-tool working directories. Changing `DISPATCH_WORKSPACE_DIR` does not generally retarget them: `DispatchRuntime.migrateWorkspaces()` handles only the specific legacy generated-directory pattern and skips unfinished work. Before restoring host state into a container or changing mount paths, inventory persisted paths and preserve narrowly scoped mappings or obtain a reviewed migration before native recovery. Do not broadly mount the host home directory to make old paths work. Use fresh disposable state for initial container qualification.

For simple file-copy backups, stop every writer and confirm exit first. Preserve file ownership/modes and complete SQLite files/journals; do not copy only selected database files from a live mount. Encrypt backups, restrict restore access and avoid giving the application task unnecessary access to the backup destination. The storage-copy/operator mechanism must be verified for S3 Files; a raw backing-bucket copy is not assumed to be a consistent filesystem backup.

Verify file restoration separately from application recovery. If a read-only SQLite integrity check cannot recover restored WAL state, open a fresh writable disposable copy with all journal sidecars preserved; leave the backup archive untouched. Do not substitute `immutable=1` merely to obtain a passing check. `integrity_check = ok` establishes structural consistency, not that every expected committed record was restored. File comparison and SQLite integrity alone do not qualify sign-in, credentials, attachments or conversation recovery.

Restore into an empty isolated destination with the complete matched set and original ownership, then start exactly one compatible task. Perform integrity and application-continuity checks using the qualification procedure before directing users to it. Retain the original store untouched until recovery is accepted. Delete temporary qualification data and credentials only after confirmed task exit and an explicit cleanup decision.
